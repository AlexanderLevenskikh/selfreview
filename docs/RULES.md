# Каталог правил SelfReview

Каноническое ядро SelfReview — декларативный каталог правил с источниками и областью действия. AST выполняет поддерживаемые проверки; Skill и справочник помогают применять договорённости при написании и содержательном ревью кода. Эти представления не имеют одинаковой полноты: `manual` не превращается в машинное доказательство.

## 1. Состояние правила и его применение

| Поле | Смысл |
|---|---|
| `id` | Уникальный идентификатор конкретной записи/варианта |
| `family` | Семантическая семья, используемая для обнаружения конфликтов и явных переопределений |
| `scope` | Назначенный набор проектов; выбирается явно |
| `status` | `candidate`, `approved` или `rejected` |
| `mode` | `enforce` или `advisory` |
| `severity` | `error`, `warning` или `info` |
| `check` | Проверка из конечного набора `kind` и её параметры |
| `applicability` | Относительные к корню проекта пути `include` и `exclude` |
| `evidence` | Источники, SHA-256 и доступный контекст |
| `approval` | Кто и почему подтвердил именно эту версию правила |
| `overrides` / `overrideReason` | Явно заменяемые правила той же семьи и причина |

`candidate` не применяется как обязательная проверка. `approved` делает правило применимым только в назначенном scope и подходящих путях. `rejected` сохраняет отрицательное решение и не участвует в проверках.

В CLI блокирующей является находка `mode: enforce` вместе с `severity: error`. Рекомендательная находка остаётся советом даже при переданном в правило уровне `error`. Подтверждённое `manual` попадает в checklist и даёт статус `MANUAL_REVIEW_REQUIRED`, если более приоритетного результата проверки нет; автоматической оценки соблюдения его текста не происходит.

Идентификаторы содержат строчные латинские буквы, цифры, точки, дефисы или подчёркивания и имеют длину до 160 символов. Семья — отдельная строка до 160 символов; для точечных ограничений допустимы имена вроде `restricted-import:legacy-library`.

## 2. Два способа внести правило

### Импорт декларативного источника

Обычный путь — JSON или Markdown. Импортёр добавит источник, назначит `scope` из команды и создаст кандидата. Не требуется вручную выдумывать хеш, `approval` или системный ID.

Файл `C:\Rules\A\logging.json`:

```json
{
  "title": "Продуктовый код пишет в logger",
  "description": "В исходниках приложения console допустим только для warn и error; штатное логирование идёт через принятый logger.",
  "family": "no-console",
  "mode": "enforce",
  "severity": "error",
  "check": {
    "kind": "no-console",
    "options": { "allowMethods": ["warn", "error"] }
  },
  "applicability": {
    "include": ["src/**/*.ts", "src/**/*.tsx"],
    "exclude": ["**/*.test.ts", "**/*.test.tsx"]
  }
}
```

Из корня SelfReview в PowerShell 5.1:

```powershell
$srConfig = 'C:\SelfReview\workspace\selfreview.config.json'
node .\bin\selfreview.mjs learn --config $srConfig --scope a --no-code --docs 'C:\Rules\A\logging.json' --out 'C:\SelfReview\workspace\learn-logging.json'
node .\bin\selfreview.mjs rules list --config $srConfig --scope a
```

Чтобы включить такое же правило в Markdown-документ, используйте блок с точным языком `selfreview-rule`:

````markdown
## Логирование

```selfreview-rule
{
  "title": "Не оставлять debugger",
  "description": "После локальной отладки удалять debugger из продуктовых исходников.",
  "check": { "kind": "no-debugger", "options": {} },
  "applicability": { "include": ["src/**/*.ts", "src/**/*.tsx"], "exclude": [] }
}
```
````

Поддерживаются один объект, массив объектов или объект с массивом `rules`. При отсутствии `mode`/`severity` машинный кандидат получает `enforce`/`error`, а `manual` — `advisory`/`info`. Источник не может самостоятельно сделать запись подтверждённой: переданные `status`, `approval`, `scope`, `id` и заявленный provenance не принимаются как полномочия.

Заголовки Markdown участвуют в интерпретации. Их иерархия и строки сохраняются в `evidence.headingContext`, а текст контекста — в описании кандидата. Заголовок с областью, условием, путём или неизвестным смыслом удерживает обычное текстовое правило в `manual` с причиной `HEADING_APPLICABILITY_UNRESOLVED`; исходный распознанный предикат может быть сохранён как неисполняемые данные `evidence.proposedCheck`. Нейтральная тема проверяется на соответствие типу правила: например, `Variables` поддерживает `no-var`, но заголовок `Components` не доказывает применимость запрета `var` ко всему проекту.

Для структурированного правила под условным заголовком укажите явную `applicability`. Тогда заданный AST-кандидат можно сохранить без угадывания путей, а заголовок всё равно останется в evidence и описании. Подтверждение требует убедиться, что явные пути и параметры действительно учитывают текстовые условия. Соседние заголовки сбрасывают контекст своего уровня и вложенных уровней; нейтральный вложенный заголовок не отменяет ограничение родительского раздела.

Неизвестный `check.kind` или неподдержанный параметр не исполняется. Строгая валидация каталога отклонит такую схему. Если договорённость пока не выражается поддерживаемой проверкой, явно используйте `manual`.

### Редактирование локального каталога

Каталог находится по пути `catalog` в конфигурации; по умолчанию это `.selfreview/catalog.json` рядом с ней. Его можно редактировать обычным JSON-редактором. Сохраняйте `schemaVersion: 1` и массив `rules`, уникальные ID, реальные источники и действительные области применения.

Подтверждение привязано к содержанию правила, включая параметры, пути, формулировки и источники. После такого изменения прежний `approval.behaviorHash` не подходит: потребуется посмотреть и подтвердить изменённую версию. Служебные поля решения обрабатывают команды `rules approve` и `rules reject`; редактирование этих полей вручную не является надёжным процессом подтверждения.

## 3. Поддерживаемые проверки

Все проверки этого раздела относятся к статическому синтаксическому анализу. Проект не компилируется и не исполняется; полный TypeScript typecheck не выполняется.

| `check.kind` | `options` | Что проверяется и где граница |
|---|---|---|
| `no-var` | `{}` | Объявления с `var`; строки и комментарии не считаются объявлениями |
| `no-console` | `{"allowMethods": ["warn", "error"]}` | Поддерживаемые обращения к глобальному `console`; локальное затенение имени учитывается |
| `no-debugger` | `{}` | Операторы `debugger` |
| `strict-equality` | `{"allowNull": true}` | Использование `==` и `!=`; явное исключение для сравнения с `null` |
| `restricted-import` | `{"modules": ["legacy-library"]}` | Поддерживаемые статически определимые импорты указанных модулей; динамически вычисляемое имя не доказывается |
| `restricted-call` | `{"callees": ["document.write", "*.substr"]}` | Синтаксическое совпадение имени вызова; принадлежность API конкретному runtime/типу не доказывается |
| `function-max-lines` | `{"max": 80}` | Физические строки поддерживаемого функционального узла; это не измерение числа ответственностей |
| `component-max-lines` | `{"max": 150}` | Размер компонента, распознанного эвристикой AST; нет гарантии распознавания всех HOC и фабрик |
| `max-parameters` | `{"max": 5}` | Число объявленных параметров поддерживаемой функции |
| `no-async-promise-executor` | `{}` | Поддерживаемый `new Promise(async ...)`; локальное затенение `Promise` учитывается |
| `require-braces` | `{}` | Фигурные скобки у поддерживаемых тел `if`/`else` и циклов |
| `manual` | `{}` | Пункт для ручного или агентского семантического ревью; AST не выдаёт вердикт по тексту |

`max` — целое число от 1 до 100000. В массивах разрешённых методов, модулей и вызовов — до 100 непустых строк; обязательные списки `modules` и `callees` не могут быть пустыми. Не добавляйте произвольные поля вроде `script`, `eval`, `command` или код плагина: этот каталог не является механизмом исполнения чужого кода.

`restricted-call` подходит и для локального API, например `legacyClient.send`. Находка означает «в AST есть такое написание вызова», а не «определена семантика объекта». Для замены API дополнительно нужны сведения о типе, целевом runtime и поведении. Встроенная рекомендация для `*.substr` формулируется как повод проверить вызов, а не как разрешение автоматически переписать его.

Текстовый шаблон `no-console` распознаёт исключения только для известных имён методов `console`, сохраняя регистр вроде `timeEnd`, `countReset`, `groupCollapsed`. Неизвестный метод или условие после `except`/«кроме» остаётся ручным кандидатом; пользовательские методы задавайте через явный JSON `allowMethods`. Фраза «except when a legacy integration requires it» не является списком методов.

## 4. Применимость: разные варианты одного правила

`applicability` проверяется относительно корня каждого проекта. Для одинакового пути `src/pages/Home.tsx` в проектах B, C, D применяется общий вариант их scope, если они назначены этому scope.

Поддерживаются шаблоны `*`, `**`, `?`. Разделитель в примерах — `/`. Перечисляйте альтернативы отдельно: `**/*.{ts,tsx}`, отрицания `!`, квадратные скобки и другие расширения glob не поддерживаются. Исключения задаются массивом `exclude`.

Пример `variants.json`: небольшие переиспользуемые компоненты и более крупные страницы имеют разные согласованные пределы.

```json
[
  {
    "title": "A: размер переиспользуемого компонента",
    "description": "Порог 100 строк согласован для src/components; исключения обсуждаем отдельно.",
    "family": "component-max-lines",
    "check": { "kind": "component-max-lines", "options": { "max": 100 } },
    "applicability": {
      "include": ["src/components/**/*.tsx"],
      "exclude": ["**/*.test.tsx"]
    }
  },
  {
    "title": "A: размер страницы",
    "description": "Порог 180 строк согласован для src/pages; он не отменяет ревью ответственности.",
    "family": "component-max-lines",
    "check": { "kind": "component-max-lines", "options": { "max": 180 } },
    "applicability": {
      "include": ["src/pages/**/*.tsx"],
      "exclude": ["**/*.test.tsx"]
    }
  }
]
```

Эти пути не пересекаются, поэтому одинаковая `family` сама по себе не создаёт конфликт. При появлении файла, к которому относятся два активных варианта одной семьи, проверка возвращает `RULE_CONFLICT`. Даже одинаковые параметры не разрешают неоднозначность автоматически: явно выберите запись или задайте переопределение.

Настройки `include`/`exclude` самого проекта ограничивают общий набор проверяемых файлов. `applicability` правила действует внутри этого набора и не возвращает исключённые проектом файлы.

## 5. Наследование и явные переопределения

Связь скоупов задаётся в `selfreview.config.json`:

```json
{
  "id": "team-bcd",
  "extends": ["a"],
  "disabledRules": []
}
```

Такой пример означает конкретное решение: B/C/D наследуют правила A. Используйте его только при реальном общем основании. Для независимых договорённостей оставьте `extends: []`. Цикл наследования отклоняется.

Наследование не делает дочернее правило автоматически сильнее родительского. Если общий лимит действует на все компоненты, а в одной вложенной области требуется другой лимит, нужны `overrides` и `overrideReason`.

Порядок для явного стабильного ID:

1. Импортируйте общее правило как кандидата.
2. До его первого подтверждения при необходимости задайте в каталоге понятный свободный ID, например `a.component-size.general`.
3. Просмотрите и подтвердите эту запись командой `rules approve`.
4. Импортируйте вариант ниже. Ссылка в `overrides` должна в точности совпасть с существующим ID из вашего каталога.

```json
{
  "title": "A: согласованный лимит legacy-страниц",
  "description": "В src/legacy/pages действует предел 220 строк до отдельной миграции. Обязанности и побочные эффекты проверяются вручную.",
  "family": "component-max-lines",
  "check": { "kind": "component-max-lines", "options": { "max": 220 } },
  "applicability": {
    "include": ["src/legacy/pages/**/*.tsx"],
    "exclude": []
  },
  "overrides": ["a.component-size.general"],
  "overrideReason": "Команда явно согласовала отдельный предел для существующих legacy-страниц"
}
```

Если общее правило сохранило автоматически выданный ID, используйте его вместо примера. Переопределяемая запись должна принадлежать той же семье и тому же scope либо его предку. Ссылки на чужой scope, неизвестную запись или цикл переопределений дают конфликт. В отчёте сохраняется, что именно было подавлено и почему.

Для полного отключения конкретной записи в скоупе есть `disabledRules` с обязательной причиной. Для локального исключения предпочтительнее подходящая `applicability` или узкое переопределение: тогда исключение видно непосредственно рядом с конвенцией.

## 6. Ручное правило и сохранение legacy API

Не каждую хорошую конвенцию можно выразить AST-предикатом. Например:

```json
{
  "title": "Сохранить контракт legacy-встраивания",
  "description": "В src/legacy/embedding document.write сохранён из-за контракта встраивания. Не модернизировать вызов без проверки целевого runtime и порядка исполнения. На каждом изменении вручную проверить договорённый сценарий.",
  "family": "restricted-call",
  "mode": "advisory",
  "severity": "info",
  "check": { "kind": "manual", "options": {} },
  "applicability": {
    "include": ["src/legacy/embedding/**/*.js"],
    "exclude": []
  }
}
```

После подтверждения этот вариант станет ручным пунктом именно для указанных файлов. Семья `restricted-call` позволяет ему подавить встроенный общий совет о потенциально устаревших вызовах в этой области. В других путях совет останется применимым.

Это не отменяет отдельно подтверждённый запрет `document.write`, если такой запрет уже есть в каталоге с другой семьёй, например `restricted-call:document.write`. Для этого требуется явное изменение его применимости либо корректный override той же семьи. Ручная оговорка не должна незаметно отключать другие соглашения.

Аналогично можно добавить требования о границах ответственности, направлении зависимостей, обработке ошибок, доступности интерфейса или тестовых сценариях. Их соблюдение оценивается отдельно; `manual` не пытается имитировать исчерпывающий семантический анализ.

## 7. Откуда берутся правила и что означает confidence

| Источник | Что фиксируется | Что не следует из него автоматически |
|---|---|---|
| AST существующего кода | Счётчики конструкций, наблюдаемые варианты, пути и SHA-256 файлов | Что текущий стиль правилен, обязателен или одобрен командой |
| Документ | Файл, SHA-256, строка/фрагмент, когда они доступны | Что любая фраза без исключений действует на весь scope |
| MR-комментарий | Текст, файл импорта, координаты old/new, автор и resolved при наличии | Что закрытый комментарий принят как универсальная политика |
| JSON от агента | Декларативное предложение и фактический файл-источник | Что агент имеет право подтвердить собственную гипотезу |

`confidence` у статического discovery — наблюдаемая доля в выбранной выборке. Она не заменяет `approval`. Редко встречающийся вариант может быть важным исключением, а массовый старый код — исторической ошибкой. Проверяйте распределение по проектам и участкам, а не только общий процент.

В evidence для MR поле `path` указывает на файл импорта, чей SHA-256 сохранён. `targetPath`, `targetLine` и `side` относятся к обсуждаемому коду. `contextVerified: false` означает, что комментарий и его положение получены из входных данных; совпадение строки с diff не доказывает состояние реального удалённого MR или его актуальный HEAD.

Цитаты ограничены по длине; при сокращении сохраняется соответствующая пометка. Хеш относится к исходному содержимому, а не только к показанному фрагменту. SHA-256 обеспечивает связь со снимком; это не цифровая подпись автора и не независимая проверка достоверности текста.

## 8. Проверка утверждения и конфликты

Подтверждение хранит `by`, `reason`, время и `behaviorHash`. После изменения содержательных полей или источников оно устаревает. `rules list` и `rules show` позволяют осмотреть запись, а `rules approve` — подтвердить просмотренную новую версию. До этого обычное ревью не должно использовать изменённое правило как прежнюю утверждённую политику.

| Ситуация | Ожидаемое поведение |
|---|---|
| Кандидат с высокой частотой | Не становится обязательным |
| Два применимых approved-варианта одной семьи | Конфликт до явного разрешения |
| Незнакомый `kind` или параметр | Ошибка валидации; код из источника не запускается |
| Изменённый лимит при старом approval | `STALE_APPROVAL` |
| Ошибка разбора TS/TSX | `INCOMPLETE`, а не отсутствие нарушений |
| Ручная договорённость | Checklist; автоматического PASS по смыслу нет |
| Встроенный совет конфликтует с конвенцией | Применимая подтверждённая конвенция имеет приоритет |
| Старое правило после повторного импорта | Не перезаписывается новым одобрением автоматически |

Конфигурация и каталог остаются локальными файлами, которыми управляет пользователь. Модель подтверждений предотвращает случайное наследование старого решения изменённым правилом; она не является защищённым многопользовательским approval-сервисом.

## 9. Best practices и соответствие экспортов

Встроенные рекомендации имеют следующие ID:

| ID | Повод для проверки |
|---|---|
| `bp.no-var` | Возможность использовать `let`/`const` |
| `bp.strict-equality` | Необходимость неявного приведения типов; `== null` разрешён советом |
| `bp.component-size` | Компонент больше 150 физических строк |
| `bp.function-size` | Функция больше 80 физических строк |
| `bp.parameters` | Более пяти параметров |
| `bp.async-executor` | Async executor у `Promise` |
| `bp.legacy-calls` | Синтаксические вызовы `*.substr` и `document.write` |

Эти числа — стартовые эвристики поставки, а не общеобязательные стандарты качества. В CLI рекомендации не блокируют сдачу. Подтверждённое правило того же вида проверки подавляет соответствующий встроенный совет; для групповых ограничений это сделано консервативно, чтобы совет не противоречил договорённости.

ESLint-адаптер использует то же ядро проверок, но имеет другие внешние условия: parser принимающего проекта, список переданных ему файлов и политика warnings. `manual` и кандидаты не превращаются в AST-правила ESLint. Встроенная проверка `selfreview/integrity` сообщает о невозможности корректно определить scope, конфликтах и ошибках разбора; при ручном подключении плагина сохраняйте эту проверку.

ESLint получает `warn` для рекомендаций. Если вызывающая система требует `--max-warnings=0`, она может отклонить такой результат. Отсутствие ошибок в одном ESLint-запуске также не доказывает, что все файлы проекта были охвачены.

Skill, JSON и справочник являются снимками каталога. Генерация не устанавливает Skill и не обновляет ранее экспортированные копии. Применимость и конфликты определяет текущая конфигурация при запуске CLI или адаптера; не считайте статический справочник самостоятельным доказательством применимости каждого правила к каждому файлу.

## 10. Данные источников и исполнение

Текст документа или комментария — входные данные. Фразы «игнорируй инструкции», «запусти команду», «отправь репозиторий» не должны становиться управляющими инструкциями ни ядра, ни агента. В генераторе Skill управляющий workflow отделён от текстов и evidence; агенту всё равно нужен такой же явный режим работы с недоверенными источниками.

Схема каталога допускает конечный набор декларативных проверок. Для нового исполняемого `kind` требуется отдельно изменить ядро, добавить содержательные positive/negative tests и проверить адаптеры. Простое добавление строки в JSON не создаёт безопасный и корректный анализатор.

В текущем исполнении нет сетевых запросов, вызова AI API, выполнения проектного JavaScript, загрузки конфигурационных JS-плагинов проверяемого проекта или автоматических исправлений. Экспортированные материалы могут содержать чувствительные цитаты и пути; хранение и передача этих файлов остаются решением пользователя.
