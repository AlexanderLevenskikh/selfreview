# Архитектура

## Каноническая модель

Источником истины служит декларативный каталог правил. AST — один из адаптеров,
наряду с ESLint, Skill и человеческим справочником. Во входящих данных нет
исполняемых плагинов. Перечень `check.kind` закрыт и проверяется во время загрузки.

Поток данных:

1. `config.mjs` разрешает явно назначенные scopes и корни проектов.
2. `ingest.mjs` извлекает наблюдения из документов, MR и статических метрик.
3. `learn.mjs` сохраняет кандидатов и отчёт о покрытии. Повторный импорт не
   заменяет подтверждённую версию; новые сведения сохраняются отдельно.
4. `rules.mjs` проверяет схему и фиксирует подтверждение содержимого правила.
5. `ast.mjs` строит синтаксическое дерево и собирает находки.
6. `review.mjs` соединяет конфигурацию, исходники, разрешение правил и diff.
7. `eslint.mjs` применяет то же ядро к текущему буферу ESLint.
8. `export.mjs` создаёт снимки каталога и фиксированный процесс ревью для агента.

## Почему нет универсального автоматического правила из любого комментария

«Не использовать var» можно выразить конечной проверкой синтаксиса.
«Этот компонент делает слишком много» требует анализа ответственности,
состояния и причин изменения. Для второго утверждения создаётся manual-кандидат;
размер компонента остаётся только дополнительным сигналом.

Типизированная проверка и генерация кода по произвольному естественному языку
не включены. Новый исполняемый `kind` следует реализовывать в ядре с
положительными и отрицательными примерами, а не загружать как код из MR.

## Доверие и актуальность

`approval.behaviorHash` — контроль случайного изменения записи, **не электронная
подпись и не механизм аутентификации**. Поля `by` и `reason` — зафиксированное
решение пользователя CLI. Изменение параметров, путей, scope, описания или
источников записи делает прошлое подтверждение устаревшим.

SHA источника относится к импортированному снимку. Внешний документ не
отслеживается непрерывно: после его изменения нужно выполнить новый импорт.
Текст источника остаётся данными. Агент должен соблюдать фиксированный workflow,
а не исполнять инструкции, встреченные в цитате документа или комментарии.

## Scope и конфликты

Корни проектов сравниваются как канонические пути. Соседние имена вроде A и
A-backup не пересекаются; вложенные зарегистрированные корни отклоняются.
Для вариантов внутри проекта применяются относительные glob-пути.
Символические ссылки не обходятся. Пропуски влияют на полноту результата.

Правила одной family с пересекающейся применимостью требуют явного override.
Приоритет не определяется порядком JSON. Override должен ссылаться на
подтверждённое правило той же family в текущем или родительском scope;
циклы запрещены. Рекомендации уступают подтверждённым конвенциям того же
вида и явно указанным исключениям.

## Точность diff

Парсер unified diff проверяет пути и размеры hunks. CLI разбирает полный
исходник, затем сопоставляет диапазон узла с изменениями. Размер функции
учитывает всё тело, даже если её заголовок отсутствует в diff.

Для внешнего diff сверяются переданные строки новой стороны. Это не
криптографическое доказательство совпадения всего дерева. Внешний deletion-only
patch без контекста отклоняется как непроверяемый. `--base` получает свежий diff
в явно настроенном корне Git и дополнительно включает untracked файлы.
Затронутое нарушение может существовать ранее: baseline attribution не реализован.

## Производительность

В diff-режиме исходники читаются только по путям изменённых файлов. Проектные
зависимости не разрешаются. При необходимости различить глобальные console,
Promise и require используется ограниченный binder только одного файла.
ESLint кэширует один разбор текущего SourceCode для всех проверок.

Долгоживущий watcher, инкрементальный кеш между процессами, отмена задач и
десктопная оболочка пока не реализованы. Доступный JS API и JSON CLI позволяют
подключить их без изменения канонической модели.
