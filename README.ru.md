# SelfReview

**Договорённости проекта, которые можно проследить до источника, подтвердить и проверить до код-ревью.**

[English](README.md) · [Русское руководство](USERGUIDE.ru.md) · [Английское руководство](USERGUIDE.md) · [Проверка](VERIFICATION.ru.md) · [GitHub Actions](https://github.com/levencode-labs/selfreview/actions/workflows/ci.yml)

SelfReview — локальный набор инструментов для JavaScript, TypeScript и React/TSX.
Он собирает **кандидатов** в правила из исходников, командных соглашений и
замечаний к merge request, хранит их в явных областях проектов (scope) и
применяет **только подтверждённые** требования через общее AST-ядро,
CLI и адаптер ESLint.

Можно создать отдельные области для проекта A, группы B/C/D и проекта E.
Один каталог экспортируется как читаемый человеком справочник, пакет
для ревью агентом либо снимок Skill. Общие best practices остаются
советами и уступают подтверждённым правилам конкретного проекта.

**Версия:** 0.2.0 · **Node.js:** 22.13+ · **Языки:** JS / TS / JSX / TSX

## Зачем нужен проект

На ревью повторяются требования, которые зависят от конкретного проекта:
какие API использовать, как организовать импорты, где допустимы legacy-исключения
и что особенно важно проверить перед открытием PR.

SelfReview переводит эти свидетельства в явный каталог. Любой импортированный
пункт начинает как **кандидат**. Человек должен проверить источник,
применимость и параметры до подтверждения. Часто встречающийся синтаксис
показывает только практику использования — не обязательную договорённость.

**Источник истины — каталог**. AST-анализ является одним способом проверить
его правила. Требования, для которых нет поддерживаемой машинной проверки,
остаются видимыми пунктами ручного ревью.

## Что реализовано

| Возможность | Текущее поведение |
| --- | --- |
| Scope проектов | Явное назначение проектов, общие области, наследование, варианты по путям, override и исключения с причиной |
| Наблюдение кода | Кандидаты `no-var`, `strict-equality` (включая сравнения с null) и `require-braces`; дополнительные метрики функций, компонентов, параметров, импортов |
| Импорт документов | Markdown, текст, JSON и структурированные предложения правил; неподдерживаемая/условная формулировка остаётся ручной |
| Импорт замечаний | Нейтральный JSON для MR, обсуждения/заметки GitLab, отдельные unified diff и комментарии |
| Подтверждение | Ссылки на источники и SHA-256, связывание решения с точным содержимым правила |
| Машинные проверки | 11 конечных видов AST-проверок и отдельный `manual` |
| Интерфейсы ревью | Текст/JSON в CLI, JavaScript API, адаптер ESLint flat config на том же ядре |
| Изменённый код | Разбор полных изменённых файлов и находки на затронутых AST-узлах; опциональное сравнение с доверенной Git-базой |
| Интеграция агента | Экспортируемые Skill, справочник и структурированный `agent-pack`; не нужен ключ AI API |
| Полнота результата | Ошибки разбора, конфликты правил, устаревшие подтверждения и недостоверный diff явно дают неполный результат |
| Жизненный цикл (0.2) | Устойчивый ID, накопление свидетельств, история решений и редакций, проверка источников, preview кандидата |
| Контекст (0.2) | Действующие правила для выбранных файлов, проверка актуальности, ручные вопросы, проверяемые примеры, точные вызовы CLI |

Машинные проверки включают объявления переменных, `console`/`debugger`,
сравнения, запрещённые импорты и вызовы, размеры функций/компонентов,
число параметров, async executor у Promise и фигурные скобки
управляющих конструкций. Точные параметры — в
[схеме правил](schemas/rule.schema.json) и [русском справочнике](docs/RULES.ru.md).

## Быстрый старт

Склонируйте репозиторий и установите зависимости из lockfile:

~~~sh
git clone https://github.com/levencode-labs/selfreview.git
cd selfreview
npm ci --ignore-scripts
node bin/selfreview.mjs --help
node bin/selfreview.mjs review --config examples/selfreview.config.json --scope team-bcd
~~~

На Windows PowerShell 5.1 вводите команды **отдельными строками**.
Если политика выполнения запрещает `npm.ps1`, используйте `npm.cmd`.
Для одного CLI достаточно `npm ci --omit=dev --ignore-scripts`;
для тестов и интеграции с ESLint нужны dev-зависимости.

Репозиторий содержит исходники, но не готовую установленную среду Node.js
и не каталог `node_modules`. Отдельный переносимый архив может включать
парсер TypeScript, но Git-клону всё равно нужна установка зависимостей.

### Проверить разные scope

~~~sh
node bin/selfreview.mjs review --config examples/selfreview.config.json --project project-a
node bin/selfreview.mjs review --config examples/selfreview.config.json --scope team-bcd
node bin/selfreview.mjs review --config examples/selfreview.config.json --project project-e
~~~

| Пример | Ожидаемый результат |
| --- | --- |
| A | Два специально внесённых нарушения; exit 1 |
| B, C, D | В общем scope разрешены `console.warn` и `console.error`; exit 0 |
| E | Явные legacy-исключения, включая политику сравнения с null; exit 0 |

`npm run demo` запускает намеренно ошибочный пример A;
его код завершения 1 — **ожидаемый результат демонстрации**.

## Подключить свои проекты

Запускайте CLI из каталога SelfReview. Замените пути на существующие
проекты и папки с соглашениями. Инструмент создаёт конфигурацию и каталог:

~~~sh
node bin/selfreview.mjs init --config ../review-data/selfreview.config.json --scope a --project ../projects/A
node bin/selfreview.mjs scope add team-bcd --config ../review-data/selfreview.config.json --project ../projects/B --project ../projects/C --project ../projects/D
node bin/selfreview.mjs scope add e --config ../review-data/selfreview.config.json --project ../projects/E
node bin/selfreview.mjs learn --config ../review-data/selfreview.config.json --scope a --docs ../agreements/A --mr ../reviews/review.json
node bin/selfreview.mjs rules list --config ../review-data/selfreview.config.json --scope a
~~~

Скопируйте **реальный** ID кандидата из вывода:

~~~sh
node bin/selfreview.mjs rules show RULE_ID --config ../review-data/selfreview.config.json
node bin/selfreview.mjs rules approve RULE_ID --config ../review-data/selfreview.config.json --by Reviewer --reason "Confirmed the team's agreement"
~~~

Проверьте изменение и создайте материалы для повторного использования:

~~~sh
node bin/selfreview.mjs review --config ../review-data/selfreview.config.json --project a --base HEAD
node bin/selfreview.mjs agent-pack --config ../review-data/selfreview.config.json --project a --base HEAD --out ../review-data/agent-pack.json
node bin/selfreview.mjs export --config ../review-data/selfreview.config.json --scope a --out ../review-data/export-a
~~~

ID проекта получаются из имён папок и выводятся в `init`.
`--base HEAD` включает локальные изменения отслеживаемых и неотслеживаемых
файлов. Для MR укажите предполагаемый базовый коммит. В режиме `--base`
зарегистрированный проект должен совпадать с корнем Git. Для обычной
проверки проекта Git не обязателен. Каталог экспорта должен быть
новым или пустым.

Подробные форматы импорта, варианты правил, утверждение, подключение
ESLint, агентов и диагностику см. в [русском](USERGUIDE.ru.md) или
[английском](USERGUIDE.md) руководстве.

## У меня уже есть база знаний — что дальше?

**Начинать всё с нуля не нужно.** Если документы Markdown/TXT/JSON для
одного проекта собраны в папку, их нужно импортировать как **кандидатов**.
Если они **уже импортированы в каталог SelfReview**, пропустите
`init` и `learn` и начните с `rules list`.

Пример для **Windows PowerShell 5.1**, из установленного
`C:\SelfReview` (зависимости Node.js уже установлены).
Замените пути и ID своими.

**1. Зарегистрируйте проект и импортируйте документы один раз:**

~~~powershell
Set-Location 'C:\SelfReview'
$srConfig = 'C:\SelfReview\workspace\selfreview.config.json'
# Только если конфигурации ещё нет; папка проекта должна существовать:
node .\bin\selfreview.mjs init --config $srConfig --scope sample-app --project 'C:\Repos\sample-app'
# Только если документы ещё не импортированы:
node .\bin\selfreview.mjs learn --config $srConfig --scope sample-app --no-code --docs 'C:\Rules\sample-app'
node .\bin\selfreview.mjs rules list --config $srConfig --scope sample-app
~~~

`--no-code` импортирует документы, не исследуя исходники.
ID `sample-app` получается из имени папки; ваш точный ID
можно проверить командой `doctor`.

**2. Посмотрите кандидата, предварительно проверьте его и только затем утвердите:**

~~~powershell
$ruleId = Read-Host 'Вставьте настоящий ID кандидата из rules list'
node .\bin\selfreview.mjs rules show $ruleId --config $srConfig
node .\bin\selfreview.mjs rules preview $ruleId --config $srConfig --project sample-app
# Только после проверки формулировки, scope, исключений и preview:
node .\bin\selfreview.mjs rules approve $ruleId --config $srConfig --by 'Reviewer' --reason 'Сверил текущую договорённость и исключения команды'
~~~

Импорт сам ничего не утверждает. Неоднозначные или неподдерживаемые
текстовые договорённости остаются вопросами ручного ревью.

**3. Перед реализацией передайте агенту правила для выбранных файлов:**

~~~powershell
node .\bin\selfreview.mjs context --config $srConfig --project sample-app --file src/Panel.tsx --out 'C:\SelfReview\workspace\task-context.json'
node .\bin\selfreview.mjs context check --config $srConfig --input 'C:\SelfReview\workspace\task-context.json'
~~~

Передайте JSON агенту и попросите соблюдать действующие правила,
рассмотреть manual-вопросы и **не утверждать новых кандидатов
автоматически**. Указанный файл может быть планируемым.
`context check` запускается **до редактирования**: после изменения
кода сохранённый снимок закономерно станет устаревшим.

**4. После изменений выполните свежую проверку и проверки самого проекта:**

~~~powershell
node .\bin\selfreview.mjs review --config $srConfig --project sample-app --file src/Panel.tsx
# Необязательно, только если C:\Repos\sample-app — корень Git:
node .\bin\selfreview.mjs review --config $srConfig --project sample-app --base HEAD
~~~

`CHECKS_PASSED` относится только к включённым AST-проверкам:
он не доказывает правильность типов, тестов, сборки, поведения и
архитектуры. `--new-only` требует доступной истории совместимой политики
в Git; внешний каталог может вызвать явно обозначенную полную проверку.
В контексте агента могут быть приватные цитаты и локальные пути:
проверьте данные перед отправкой облачной модели.

Когда документы изменились, используйте `sources status` и
`sources refresh`. Чтобы обнаружить **новые файлы** в папке,
запустите `learn --docs` ещё раз. Полные примеры — в
[русском руководстве](USERGUIDE.ru.md).

## Как читать результат

| Код завершения | Значение |
| --- | --- |
| 0 | Команда завершена без блокирующего нарушения включённого AST-правила |
| 1 | Найдена ошибка по подтверждённому обязательному правилу |
| 2 | Ошибка конфигурации либо неполный анализ |

Код 0 **не** означает, что весь MR одобрен.
`ADVISORY_ONLY`, `MANUAL_REVIEW_REQUIRED`, `NOT_APPLICABLE`
и `NO_CHANGES` имеют разные ограничения покрытия.
Ручные правила остаются чек-листом, а советы не утверждаются
автоматически как конвенции.

## Ежедневный процесс и актуальность правил

Эквивалентные свидетельства теперь накапливаются у устойчивого
логического ID. Утверждённые и отклонённые снимки сохраняются;
изменившееся правило становится кандидатом на пересмотр, но не
автоматическим обновлением политики. Перед решением можно посмотреть
его последствия:

~~~sh
node bin/selfreview.mjs sources status --config selfreview.config.json --scope team
node bin/selfreview.mjs sources refresh --config selfreview.config.json --scope team
node bin/selfreview.mjs rules history RULE_ID --config selfreview.config.json
node bin/selfreview.mjs rules preview RULE_ID --config selfreview.config.json --project app
~~~

Контекст для точных файлов, включая будущие, содержит применимые
правила, вызовы CLI, проверяемые примеры, manual-вопросы, состояния
источников и хеши согласованности:

~~~sh
node bin/selfreview.mjs context --config selfreview.config.json --project app --file src/example.ts --out task-context.json
node bin/selfreview.mjs context check --config selfreview.config.json --input task-context.json
node bin/selfreview.mjs review --config selfreview.config.json --project app --file src/example.ts
~~~

Актуальность проверяется **перед** редактированием. После правок
нужно сделать новую проверку кода и создать новый контекст.
Только примеры с `PASS` прошли заявленную синтаксическую
проверку; manual и старые произвольные примеры не удостоверены.

Если политика находится в Git, `review --base origin/main
--merge-base --new-only` сравнивает находки на базе и в текущих файлах.
`--staged` читает индекс Git, который может отличаться от рабочего
дерева. Изменение политики или недоступная историческая политика
ведёт к видимому fallback на полное ревью, а не ложному заключению
«новых ошибок нет». Обычный `--base` по-прежнему проверяет
затронутые узлы.

Контракты и критерии: [план развития](IMPLEMENTATION_PLAN.ru.md),
[рабочий процесс](docs/WORKFLOW.ru.md), раздел 11
[русского руководства](USERGUIDE.ru.md#11-поддерживать-правила-и-готовить-ежедневную-задачу).

## Проверки и известные ограничения

Для 0.2.0 в локальной проверке прошло **163 теста**, без ошибок/пропусков,
повторно разобраны **229** выбранных публичных файлов и выполнены
**17/17** зафиксированных workflow-сценариев.
Сопоставимый исторический прогон дал 5 PASS, 3 FAIL и 9 NOT_AVAILABLE.
Синтаксические результаты совпали с эквивалентно настроенным ESLint:
преимущество в общем обнаружении этих синтаксических ошибок
**не заявляется**. Улучшения относятся к жизненному циклу и ревью.
См. [проверку 0.2.0](verification/workflow-v0.2/README.ru.md) и
[результаты workflow](evaluation/workflow/RESULTS.ru.md).

Первоначальная локальная проверка на Linux/Node.js 24.22.1:
**107 тестов** без пропусков, включая subprocess CLI и настоящий
ESLint. Сохранённая оценка на исходниках разобрала **229** выбранных
файлов из закреплённых ревизий `p-limit`, `usehooks-ts`,
`underscore`. Синтетические примеры включают различные стили, разные
scope, условные документы и замечания к MR.

Это ограниченные проверки конкретной реализации, **не** универсальный
показатель точности. В репозитории сохранены исходные неудачные результаты,
последующие исправления и отдельно разобранная ошибка выбора документа
в оценщике. См. [исторический отчёт](VERIFICATION.ru.md),
[происхождение публичной оценки](evaluation/public/provenance.json)
и [историю синтетической проверки](evaluation/synthetic/RESULTS.ru.md).

**Ограничения:**

- Discovery не восстанавливает все командные соглашения. Из частот
  автоматически предлагаются только три семейства; остальные факты
  остаются свидетельствами или manual-кандидатами. Противоречивые
  стили проектов препятствуют общей гипотезе.
- Размер компонента — эвристика. Ответственности, бизнес-логика и
  архитектура требуют содержательной оценки.
- Проверки имен API не выполняют полного анализа типов и потоков данных:
  алиасы и одноимённые посторонние методы требуют ручной оценки.
- Обычная проверка diff показывает затронутые AST-узлы, которые могут
  содержать старые нарушения. Опциональный `--new-only` требует
  анализируемой доверенной Git-базы и совместимой исторической политики;
  fallback и неполнота явно отражаются в отчёте.
- Поддерживаются `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.cjs`,
  `.mts`, `.cts`. Нет поддержки Flow, Vue/Svelte SFC, C#, импорта PDF
  и DOCX.
- Анализатор не запускает код, зависимости, сборки или тесты
  проверяемых проектов и не заменяет этих проверок.
- Git-режимы требуют поддержку `git --no-lazy-fetch`. Отсутствующие
  объекты вызывают ошибку без загрузки; бинарные патчи остаются
  неполными даже при отсутствии затронутых JS/TS-файлов.
- Нет desktop-приложения, размещённого сервиса, watcher и
  автоматической установки Skill. CLI и экспорты работают локально
  без вызовов AI API.

Нативное выполнение Windows **не входило** в первоначальную локальную
проверку. В GitHub Actions есть матрица Ubuntu/Windows × Node 22/24.
Первоначально она выявила проблему сравнения корня Git на Windows;
исправление проверяет корень средствами Git. История ошибок, правки
и актуальные ссылки — в [CI follow-up](verification/GITHUB_CI.ru.md).
Для 0.2.0 размещённые проверки PR и main прошли по 4 задания.

## Разработка

~~~sh
npm ci --ignore-scripts
npm test
node evaluation/public/run.mjs
~~~

Публичный прогон использует сохранённые исходники и **не**
устанавливает/исполняет код проверяемых проектов. Исторические
синтетические runner защищают результаты от перезаписи:
см. [VERIFICATION.ru.md](VERIFICATION.ru.md) для процедуры.

`SOURCE_MANIFEST.json` сохраняет файловый состав исходной переносимой
поставки; хеши документации относятся к тому состоянию до
добавления GitHub-руководств. `PUBLICATION_MANIFEST.json` фиксирует
первую публикацию репозитория; последующие коммиты — отдельные
версии. Абсолютные пути в исторических артефактах относятся
к среде первоначального запуска.

| Путь | Содержимое |
| --- | --- |
| `src/` | Каталог правил, scope, импорт, AST-ядро, отчёты, адаптеры |
| `bin/` | Точка входа CLI |
| `schemas/` | Схемы конфигурации и правил |
| `examples/` | Пять синтетических проектов, соглашения, MR-входы, утверждённые примеры |
| `test/` | Проверки ядра, границ, CLI, ESLint |
| `evaluation/` | Публичные/синтетические корпуса, происхождение, исторические результаты |
| `verification/` | Артефакты записанной проверки |

Инварианты разработчика — в [AGENTS.ru.md](AGENTS.ru.md).
Архитектура — в [docs/ARCHITECTURE.ru.md](docs/ARCHITECTURE.ru.md);
справочник — в [docs/RULES.ru.md](docs/RULES.ru.md).

## Лицензирование
